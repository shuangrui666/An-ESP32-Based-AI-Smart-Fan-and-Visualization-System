# SmartFan 2.0 智能化升级方案

- 状态：已完成主要软硬件模块开发；整机端到端联动仍待补充验证
- 最近更新日期：2026-11-25
- 主控平台：YD-ESP32-S3 Classic V1.0 / ESP32-S3-WROOM-1
- 关联实验与文档：EXP-001（DHT11）、EXP-004（Wi-Fi/HTTP 数据上传）、EXP-009（PIR）、EXP-012（MOSFET 风扇驱动）、Phase 3.2.1（后端指令队列）、Phase 3.2.2（前端控制与指令状态处理）

## 1. 原设备现状与升级基础

本项目以一台 USB 供电的 5V 小型风扇为执行对象，增加传感器、嵌入式控制、无线通信、后端服务和网页可视化能力，形成 SmartFan 2.0。

| 项目 | 已知信息 | 信息性质/限制 |
|---|---|---|
| 风扇供电 | USB 5V；商家标称 1A，说明书另有 2.5W 信息 | 属于产品资料，不是本项目实测电流或功率 |
| 风扇控制 | 通过外置 MOSFET 模块切换/调节风扇负载供电 | 已完成 GPIO6 独立驱动基本测试；中间 PWM 档位仍需系统化验证 |
| 主控 | ESP32-S3-WROOM-1，YD-ESP32-S3 Classic V1.0 | 开发环境使用 PlatformIO，目标环境 esp32-s3-devkitc-1 |
| 温湿度传感器 | DHT11，DATA 接 GPIO4，3.3V 供电 | 已有 EXP-001 记录，22/22 次读取成功 |
| 人体检测 | HC-SR501 PIR，OUT 接 GPIO5，模块使用 5V 供电 | 已有 EXP-009 信号测试记录；未完成距离、角度及误触发率测试 |
| 通信 | ESP32 通过 Wi-Fi 与 Flask 后端通信 | 已有 EXP-004 历史 HTTP 200 数据上传记录 |
| 网页 | HTML/CSS/JavaScript/ECharts 前端 | 已实现温湿度展示、图表、手动档位、AUTO/MANUAL 模式和指令状态查询界面 |

原风扇内部电路、原生控制协议和内部控制板接口没有经过拆机或电气测量确认。本方案采用外置 MOSFET 控制风扇供电回路，不把 ESP32 GPIO 直接连接到风扇电机，也不假定原风扇内部存在可直接使用的 PWM 控制接口。

## 2. 智能化升级目标与实现情况

### 2.1 升级目标

1. 感知环境：通过 DHT11 获取温度、湿度，通过 PIR 检测人体活动。
2. 本地控制：ESP32-S3 根据传感器数据和控制策略决定风扇启停及档位。
3. 功率驱动：通过 MOSFET 模块控制独立 5V 风扇负载回路。
4. 无线通信：ESP32-S3 通过 Wi-Fi 向 Flask 后端上传传感器数据，并获取网页下发的控制指令。
5. 可视化与交互：网页展示温湿度和设备状态，支持手动档位控制、自动/手动模式切换及指令状态查询。
6. 智能策略：根据人体活动和温度阈值进行规则控制；后续可在积累数据后升级为数据驱动模型。

### 2.2 模块完成度

## 3. 系统总体结构

系统采用“传感器感知—ESP32 本地控制—Wi-Fi 通信—Flask 服务—网页交互”的分层结构。

```text
DHT11 (GPIO4) ─┐
               ├──> ESP32-S3 ──Wi-Fi──> Flask 后端 <──> Web 前端
PIR (GPIO5) ───┘       │                    │               │
                       │ GPIO6              │ 指令队列      │ 手动/自动控制
                       v                    │               │
                    MOSFET <────────────────┘               │
                       │                                    │
                  独立 5V 供电                               │
                       │                                    │
                    USB 风扇 <───────────────────────────────┘
```

说明：网页并不直接驱动 GPIO。网页控制请求先到达后端，由 ESP32 轮询获取指令、执行控制并回报状态。上图表达目标数据与控制路径；各环节的软件实现和模块实验不等同于完整端到端实机联动已经通过。

## 5. 控制策略与状态管理

### 5.1 自动控制策略

当前自动控制采用规则策略，而不是已训练的机器学习模型：

- 当检测到人体活动，且温度达到自动启动阈值（当前代码记录为 28°C）时，允许启动风扇。
- 当检测到人体活动但温度低于 28°C 时，不因 PIR 触发而自动启动风扇。
- 人员离开或持续未检测到人体后，按设定的空闲延时关闭风扇；现有设计记录的延时为 60 秒。
- 温度低于关闭阈值（设计记录中提及 26°C）时，可按自动控制策略关闭风扇；最终行为应以当前固件配置和实机测试记录为准。
- DHT11 读取失败时采取安全策略，避免因无效温度数据持续驱动风扇。
- 手动模式下允许用户通过网页主动选择档位，即使温度未达到自动启动阈值也可以手动开启，以保留用户主导权（FR-014）。

### 5.2 手动控制与通信策略

- 网页提供 AUTO/MANUAL 模式和 0–5 档控制入口。
- 手动控制指令由 Flask 后端接收并进入指令队列，ESP32 通过 Wi-Fi 轮询获取指令。
- 指令包含有效期信息；Phase 3.2.1/3.2.2 设计记录了状态流转和剩余有效期处理。
- 网络中断时按既定设计保持当前手动状态；ESP32 重启后恢复自动模式。
- 后端指令状态、ESP32 执行结果和网页显示应通过 command_id 对应，避免仅凭按钮点击就认定风扇已执行。

### 5.3 状态与异常处理

| 场景 | 设计处理 | 验证边界 |
|---|---|---|
| AUTO 模式 | 根据人体检测、温度和延时规则控制风扇 | 需补充传感器到风扇的完整联动记录 |
| MANUAL 模式 | 接收网页档位指令，允许用户主动控制 | 有前后端实现与 API 测试记录；完整实机闭环待验证 |
| Wi-Fi 断开 | 保持当前手动状态 | 属于 Phase 3.2.2 设计决策，仍应补充断网实测 |
| ESP32 重启 | 恢复 AUTO 模式 | 属于设计决策，仍应补充重启实测 |
| DHT11 读取失败 | 采用安全关闭策略 | 应补充故障注入或断线测试证据 |
| 指令过期/取消/失败 | 后端和设备侧按指令状态处理，不应继续执行过期命令 | 后端队列测试已有记录；设备侧全链路待验证 |

## 8. 风险、限制与后续升级

1. **电气安全：** 必须确认 MOSFET 模块额定电压、电流和散热能力适合风扇负载；检查电源极性、接线牢固度和公共参考地。未测得的电流、温升和波形不得写成实测值。
2. **PWM 与档位映射：** 当前有基本开关驱动证据，但 0–5 档的实际转速/风量对应关系尚需测量。不能仅凭软件百分比推断实际转速。
3. **PIR 局限：** PIR 检测的是红外变化，不等同于精确人数或持续在场识别；需要结合延时策略减少误关机。
4. **温湿度精度：** DHT11 适合基础环境监测，不应将其视为高精度测量设备。
5. **网络可靠性：** Wi-Fi 或后端不可用时，设备应保持安全、可预测的本地行为；需进行断网恢复和设备重启测试。
6. **后端持久化：** 当前指令队列测试不代表已有数据库持久化能力；后续可增加数据库存储、设备认证、日志追踪和多设备管理。
7. **智能算法：** 当前采用可解释的阈值与状态规则。后续收集足够的温湿度、人体活动、用户档位和舒适度反馈数据后，再评估训练舒适度预测或风扇档位推荐模型；在模型训练和验证完成前，不宣称已实现机器学习控制。
8. **课程预算：** 需要补齐增量器件的真实采购价格和来源，并按课程要求核对 20 元预算口径。

## 9. 总结

本次升级已形成由 DHT11、PIR、ESP32-S3、MOSFET、Flask 后端和网页前端组成的智能风扇系统框架。传感器采集、人体检测、基础风扇驱动、无线数据上传、后端指令队列及网页控制软件均有相应实现或阶段性记录。当前最重要的收尾工作不是重新设计系统，而是补齐网页控制到实体风扇执行的端到端实测证据、自动控制场景验证、PWM 档位测量和真实 BOM 价格凭证。

本方案如实区分了已实现功能、模块级验证、设计约定和待验证事项，可作为课程项目智能升级设计与实施过程的说明文件。
